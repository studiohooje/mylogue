## 마웨로그의 추가 요구사항

- 체중·체지방률·골격근량 각각 입력, 수정, 삭제, 기간별 그래프와 측정일 비교.
- 인바디 사진 첨부 → 문자·숫자 추출 → 필드별 확인·수정 → 확정 저장. 원본 사진 보관 여부는 별도 선택.
- 채팅 경유 가져오기: 대표님이 인바디 사진을 Codex에 제공 → 수치 추출과 원본 대조 → 버전이 있는 마웨로그 JSON 파일 생성 → 앱에서 미리보기·검증·확정 저장. 누락·판독 불가 값은 추측하지 않고 비워둔다.
- 식단: 하루 총칼로리와 탄수화물·단백질·지방의 g, 열량 기준 비율, 목표 대비 진행률.
- 운동: 번핏 공유 이미지처럼 주요 수치와 운동 부위를 읽기 쉬운 결과 카드로 표현하되 자체 디자인·에셋 사용.
- 세 기록을 한 날짜에 묶는 홈·캘린더·기록 습관 흐름.

## 세부 구현 전에 확인할 미해결 항목

1. 번핏 앱 내부의 Pro 전체 메뉴, 화면 간 이동, 세트 추천 규칙, 피로도·칼로리 산식은 공개 설명으로 확정 불가. 화면 기록이 있으면 기능 명세의 정확도를 높일 수 있다.
2. 인바디 OCR은 결과지 기종·레이아웃·촬영 품질에 따라 다르므로 샘플을 통한 정확도 검증 필요.
3. 음식 사진에서 영양소를 추정하는 기능은 사진만으로 정확한 중량·조리법을 알 수 없다. 사용자 확인이 필요하다.
4. 식품 영양 DB를 붙일 경우 출처·라이선스·갱신 방식 결정 필요.
5. 생성형 AI 분석은 온디바이스 모델 성능 또는 외부 API 비용·데이터 전송 결정이 필요하다.
6. 개인용 로컬 저장은 운영비를 낮추지만 기기 분실·교체에 대비한 백업이 필요하다.
7. Codex가 앱에 직접 기록하려면 마웨로그가 인증된 쓰기 API 또는 연결 도구를 제공해야 한다. 앱 개발·설치만으로 이 채팅과 자동 연결되지는 않는다.
8. 최종 목표는 서버 저장과 기기 간 동기화. 기록별 고유 ID·수정 시각·스키마 버전·삭제 상태를 정의하고 저장소 계층을 분리한다. 서버 선택 시 인증·접근 규칙·사진 저장·충돌 해결·백업 정책을 함께 설계한다.

## 목업 단계의 설계 입력

- 최소 5개 서로 다른 정보 구조. 세 영역의 빠른 기록과 추세 확인을 같은 기능 세트로 비교.
- 벤토 그리드: 요약 카드에만 후보. 바텀 시트: 짧은 입력. 칩: 날짜·끼니·부위 필터. 스낵바: 저장·취소. 스켈레톤: OCR·AI 대기. FAB: 빠른 기록 진입 여부를 비교.
- 검정·밝은 회색·보라 두 톤, Pretendard, Tossface 이모지. 기능 아이콘은 별도 일관된 세트 필요.
- 한국어 줄바꿈은 단어 단위로 관리하고 모바일 폭에서도 숫자·단위·조사를 고립시키지 않는다.
