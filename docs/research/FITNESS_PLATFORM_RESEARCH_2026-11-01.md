## 핵심 결론

마웨로그의 경쟁력은 앱 기능을 무작정 합치는 데 있지 않다. **기록을 빠르게 남기고, 잘못되거나 빠진 데이터를 정직하게 표시하며, 몸·식단·운동의 변화를 한 날짜에서 이해하게 만드는 것**이 대표님 목적과 가장 맞다. 첫 보완은 실기기에서 안전한 저장·복원과 편집이다. 그다음 반복 식사·운동의 입력 단축, 마지막으로 근거가 보이는 추세/제안이다. AI·서버·워치는 명시된 보류/추후 연결 상태를 유지한다.

## 4. 대표님 추가 요구 — 마웨로그 고유 그림체와 선택형 운동 기록

2026-11-01 추가 지시: **근육별 운동 타깃을 몸 그림에서 빨간색으로 표시하고, 프리웨이트·머신 모두 연결한다. 머신의 외형도 마웨로그만의 그림체로 보여준다. 지금의 직접 입력 중심 운동 기록을 선택형으로 바꾼다.** 다음 명세는 Astra가 구현할 **디자인·개발 과제**다. 현재 앱에 완성된 그림 자산이나 선택형 전 흐름이 있다는 뜻이 아니다.

### 4.1 독자적 시각 언어 — ‘마웨로그 운동 도감’

| 구성 | 화면·자산 명세 | 데이터·작업 기준 |
|---|---|---|
| 인체 전·후면 | 단순한 해부학 실루엣을 **자체 제작 SVG/벡터**로 만든다. 짙은 검정/차콜 몸체, 밝은 회색 윤곽, 기존 두 보라를 비활성 부위·선택 상태에 사용한다. **주동근은 선명한 빨강**, 보조근은 낮은 채도의 적색 또는 해칭으로 구분하고 범례·문자 라벨을 붙인다. 빨강만으로 의미를 전달하지 않는다 | 모바일 360px에서도 선택 부위가 구분되고 스크린리더에는 근육 이름·주/보조 타깃을 읽어준다. 번핏의 근육 그림/도형 경계/포즈를 트레이싱하지 않는다 |
| 근육 지도 | 대흉근 상/중/하부, 삼각근 전/측/후, 광배·승모·기립근, 이두·삼두·전완, 복근·복사근, 둔근, 대퇴사두·햄스트링·내전근·종아리 등 **표시할 수 있는 수준의 영역만** 정한다. 모든 운동에 억지로 미세 근육을 지정하지 않는다 | 운동 카탈로그에 `primaryMuscleIds[]`, `secondaryMuscleIds[]`, `anatomyMapVersion`을 둔다. 사용자 종목도 주/보조 타깃을 선택. 해부학적 관계는 동작·자세에 따라 달라질 수 있으므로 ‘일반적인 타깃’으로 표시하고 검토한다 |

### 4.2 직접 입력을 줄이는 선택형 운동 흐름

1. `운동 시작` → `최근 / 즐겨찾기 / 내 루틴 / 부위 / 장비(프리웨이트·머신 등)` 선택. 텍스트 검색은 보조 경로로 남긴다.
2. `부위`를 누르면 인체 전·후면의 근육을 터치해 타깃 운동 카드를 필터링한다. 운동 카드를 누르면 해당 주동근은 빨강, 보조근은 별도 패턴으로 미리 본다.
3. 머신 운동이면 제조사→모델을 기존 머신 프로필에서 선택한다. **‘모름/목록에 없음’**을 항상 제공하고 새 머신 등록 또는 사진 식별 후보로 이동한다. 한 동작의 머신별 이전 기록을 구별해 보여준다.
4. 세트 화면은 지난 기록/루틴 목표를 **편집 가능한 시작값**으로 채운다. 중량은 `−/+` 스텝 버튼과 숫자 입력을 함께 제공하고 kg/lb 선택, 횟수는 퀵 선택 칩/스텝 버튼, 세트 유형·RPE는 칩/슬라이더/선택지로 입력한다. 한 세트를 완료하면 바로 다음 세트와 타이머로 이어진다. 사용자는 항상 수치를 직접 수정할 수 있다.
5. `세트 복사`, `지난 세트 적용`, `이전 운동 전체 복사`, `운동 순서 변경`, `실수 되돌리기`, `임시 저장 후 이어하기`를 검토한다. 운동 중 화면을 닫거나 전화가 와도 작성 중인 세션을 잃지 않게 한다.
6. 완료 화면은 운동별 주/보조 타깃, 부위별 실제 완료 세트, 머신 모델/단위, 이전 대비 변화와 다음 제안 근거를 **마웨로그 도감 그림체**로 표시한다.

**입력 성능 수용 기준:** 즐겨찾기 종목을 골라 전회와 동일한 세트 3개를 기록하는 흐름을 실제 Android/iPhone에서 시연하고, 키보드가 필요한 단계와 화면 탭 수를 측정한다. 최초 종목과 머신 미등록 사례도 막힘없이 수동 완료 가능해야 한다. 입력 도중 앱 재시작→임시 세션 복구, kg/lb 혼합 세트, 근육 그림의 화면/스크린리더 표시를 검증한다.

## 5. 대표님 추가 요구 — 피로·컨디션을 반영한 다음 운동 제안

**질문에 대한 설계 답:** 몇 세트·몇 kg·몇 회를 했는지 알면 어느 부위에 **얼마나 운동 부하가 기록됐는지 추정**할 수 있다. 그러나 같은 숫자라도 동작 범위, 머신 구조, 운동 숙련도, 세트 실패 여부, 수면, 통증, 스트레스 등에 따라 실제 피로와 회복은 달라진다. 따라서 현재의 ‘기록만을 이용한 단순 제안’에서 멈출 필요는 없지만, 기록만으로 몸의 건강 상태를 **확정**해서도 안 된다. [저항운동 모니터링 리뷰](https://pubmed.ncbi.nlm.nih.gov/26780346/)는 운동 자극을 단일 중량/볼륨만으로 포착하기 어렵고 주관적 강도·자가 상태 평가를 함께 볼 수 있음을 설명한다. [Fitbod](https://help.fitbod.me/hc/en-us/articles/43492170863895-How-does-Fitbod-know-my-muscles-are-still-recovering)도 회복률을 측정값이 아닌 추정 모델로 설명하고 사용자가 조정하게 한다.

| 단계 | Astra 구현 명세 | 사용자에게 보일 것 / 보류 조건 |
|---|---|---|
| 입력 1: 실제 운동 부하 | 완료된 본세트 중심으로 종목·주/보조 근육·세트·반복·중량·RPE·실패 여부·운동 날짜를 합산. 워밍업과 유산소는 별도 규칙. kg/lb는 통일 단위로 계산하되 머신 모델별 중량을 다른 머신의 실부하와 동일시하지 않는다 | 부위별 ‘최근 운동 자극’과 근거 세트. 입력이 없거나 종목 타깃이 불명확하면 부위 판단 보류 |
| 입력 2: 시간 | 운동 후 경과 시간, 최근 7·14일 세트 분포와 개인의 평소 기록량을 비교. 고정된 ‘48시간이면 100% 회복’ 규칙은 사용하지 않음 | 마지막 운동일·최근 세트 수·평소 대비 변화를 보여줌 |
| 입력 3: 오늘 상태 | 짧은 체크인: 수면 만족도, 전신 에너지, 해당 부위 근육통/뻣뻣함, **통증·부상 우려**, 원할 경우 스트레스/컨디션. 입력은 건너뛸 수 있지만 그러면 ‘오늘 상태 미확인’ 표시 | 통증/부상 우려가 있으면 해당 부위의 중량·세트 증량 추천 금지. 심한/지속 통증은 진료가 필요한지 사용자에게 확인하도록 안내 |
| 모델 | 마웨로그 자체의 **설명 가능한 ‘추정 운동 부하’와 ‘오늘 준비 상태’**를 분리. 세트의 주/보조 근육 가중, RPE, 최근 누적과 시간 경과의 규칙을 공개·테스트하고 사용자 피드백으로 조정. 첫 버전은 ‘부담 큼/보통/자료 부족’ 같은 범주와 신뢰 수준을 사용하며 의학적 `회복률 83%` 등 정밀값을 만들지 않음 | 사용자 화면에 ‘기록 기반 추정’과 ‘자가 입력 상태’를 구분, 규칙·반영한 날짜·미입력 항목·신뢰 낮음 표시 |
| 추천 | 부위 후보 1~3개와 종목·세트·중량 **편집 가능한 초안**. 최근 같은 부위에 고부하 기록이 있고 근육통/에너지 저하가 있으면 다른 부위 또는 낮은 강도/휴식 옵션을 제시. 컨디션 양호·충분한 기록이 있을 때만 점진 과부하 초안 제시 | 각 제안의 ‘왜’(지난 운동 날짜/완료 세트/RPE/오늘 상태)와 `수정·건너뛰기·내가 정하기` 선택지 |
| 검증 | 실제 입력 패턴(기록 없음, RPE 누락, 연속 운동, 머신 교체, 통증, 긴 공백, 한쪽 부위만 기록)을 테스트하고 사용자의 체감 피로와 제안이 어긋나면 사용자가 상태를 수정하도록 한다 | 미검증 모델을 ‘건강 상태 측정’이나 안전한 운동 처방으로 표현하지 않음. 실제 경험과 차이가 나는 사례를 수집해 규칙 수정 |

**UX 문구 방향:** 기존의 단순 문구를 없애고 `최근 등 운동 2회·완료 14세트와 오늘 입력한 근육통을 바탕으로, 등 대신 하체·가벼운 유산소를 먼저 보여드립니다. 운동할 부위와 강도는 직접 바꿀 수 있습니다.`처럼 **근거와 한계를 함께** 적는다. 데이터가 적으면 `최근 기록이 부족해 피로를 판단하기 어렵습니다. 오늘 상태를 입력하거나 직접 운동을 고르세요.`라고 표시한다. 이 문구는 예시이며 실제 계산과 일치할 때만 사용한다.

**구현 의존성:** 근육 지도/종목 타깃 ID(§4) → 완료 세트·RPE·머신/단위 정규화 → 사용자 상태 입력과 저장 → 추정 규칙·테스트 → 설명 가능한 추천 UI. 외부 AI나 워치 연결 없이도 **규칙 기반 첫 버전은 개발 가능**하다. 이후 AI를 붙여도 AI는 근거 없는 숫자를 만들지 않고 사용자 확인을 거치게 한다.

## 6. Astra 후속 작업 원칙 — 기능은 참고하고, 제품은 독자적으로

1. 번핏/타 앱에서 배울 대상은 **사용자 문제와 기능적 흐름**이다. 예: 지난 세트를 보며 현재 세트를 빨리 기록, 반복 식사를 복사, 측정값의 추세를 비교. 화면 좌표·레이아웃의 독특한 조합, 카피·아이콘·삽화·GIF·상표·에셋·프로그램 문구·비공개 코드/산식은 가져오지 않는다.
2. 마웨로그의 독자적 중심 개념은 **‘오늘의 세 기록 → 기록 신뢰도 → 내 변화 → 다음 한 행동’**이다. 세 영역을 같은 날짜 축에 놓고, 데이터가 비면 ‘모름’이라고 말하며, 사용자가 언제든 수정할 수 있게 한다. 이는 이 조사에서 도출한 **제품 제안**이지 기존 앱의 확인된 기능 명칭이 아니다.
3. 기존 블랙·밝은 회색·두 보라, 마웨그에서 이어온 이름/그래프, Pretendard/Tossface 지향을 유지하되 실제 폰트·아이콘 파일의 사용권과 로딩을 검증한다. 마웨로그의 고유 정보 구조·명칭·카드·그래프·애니메이션을 설계하고, 출처 앱 화면을 픽셀 단위로 재현하지 않는다.
4. 계산 규칙은 마웨로그의 코드와 설명으로 작성한다. 추정 1RM·주간 세트·체중 평활화·추천 중량의 입력값과 가정을 사용자에게 보이고, 데이터가 부족하면 제안을 보류한다. 다른 앱의 내부 알고리즘과 동일하다고 주장하지 않는다.
5. 기능을 더할 때마다 **현재 코드 → 새 동작 → 화면 경로 → 데이터/백업 호환 → Android/iPhone 검증 → 한계**를 체크한다. 특히 새 분석 기능이 실제 입력·복원 문제를 가리지 않게 한다.
6. 사용자 1~2명의 **사적 건강 기록**이 기본값으로 외부 전송·공유되지 않도록 한다. 서버·AI·OS 건강 데이터 연동은 나중에 별도 연결·권한·출처·중복 처리 설계가 필요하다. 현재 워치 연동은 대표님 결정대로 보류다.
