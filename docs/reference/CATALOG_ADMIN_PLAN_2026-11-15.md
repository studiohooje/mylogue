# 공용 도감·관리자·등록 요청 설계 초안 — 2026-11-15

상태: 대표님이 운영 원칙을 확정함. 구현 전 기획 검토용 문서이며 현재 서비스 기능이 아니다.

## 확정 원칙

1. 음식·운동·제조사별 머신 모델 도감은 향후 모든 가입자가 읽는다.
2. Codex가 검증해 소스에 등록한 기본 데이터보다 서버의 관리자 수정값을 우선한다.
3. 개인 운동·식단 기록은 계정별로 분리한다. 과거 기록은 당시의 영양값·종목 정보를 스냅샷으로 보존한다.
4. 공용 머신 모델과 헬스장 지점의 실제 보유 머신을 별도 엔티티로 저장한다. 지점 정보는 관리자 승인 후 공개한다.
5. 사용자 머신 요청은 사진 첨부 또는 제조사·모델 직접 입력을 선택한다. 사진 자동 식별은 이번 범위에서 제외한다.
6. 관리자는 요청을 검토하고 Codex에 별도 조사·등록을 지시한다. 일반 사용자는 공용 도감을 직접 변경하지 못한다.

## 데이터 모델 제안

| 데이터 | 필드 핵심 | 읽기 | 쓰기 |
|---|---|---|---|
| `catalogFoods` | 안정 ID, 이름·제조사·바코드, 기준량·단위, kcal·탄·단·지, 출처·검증일·버전 | 모든 로그인 사용자 | 관리자만 |
| `catalogExercises` | 안정 ID, 이름·별칭, 장비·동작 유형, 주·보조 근육, 참고 출처·버전 | 모든 로그인 사용자 | 관리자만 |
| `machineModels` | 제조사·정확한 모델, 연결 종목, 저항 방식·단위, 타깃 검증 근거·버전 | 모든 로그인 사용자 | 관리자만 |
| `gymLocations` | 지점 이름·위치, 공개 상태·검증 상태 | 공개 승인 시 모든 로그인 사용자 | 관리자만 |
| `gymMachines` | 지점 ID, 머신 모델 ID, 사용자별 로컬 별칭과 분리 | 공개 승인 시 모든 로그인 사용자 | 관리자만 |
| `catalogRequests` | 요청자 UID, 요청 종류, 입력값, 사진 경로, 상태, 관리자 메모, 생성 시각 | 본인 요청·관리자 | 본인 신규 요청·관리자 상태 변경 |

소스의 기본 도감과 서버 수정값은 안정 ID로 병합한다. 기존 사용자 음식과 운동은 개인 데이터로 유지한다. 충돌 시 `개인 선택값 > 관리자 서버 수정값 > 소스 기본값`을 표시하되, 개인 선택값을 공용 도감으로 자동 승격하지 않는다. 기존 기록의 영양 수치와 운동 세트는 재계산하지 않는다.

## 입력 흐름

### 음식

- 빠른 검색: `최근 → 내 음식 → 공용 도감 → 직접 등록` 순서. 검색 실패 시 `+ 새 음식 직접 등록`을 검색창 바로 아래에 둔다.
- 직접 등록: 이름, 제조사 선택, `100g / 1개 / 1회` 기준, kcal·탄·단·지, 값 출처, 먹은 양, 미리보기, 저장. 빈 값과 0을 구분하고 기준량을 명시한다.
- Codex 등록: 대표님이 제품명·라벨 사진/공식 자료를 주면 근거와 기준량을 검증해 소스 기본 도감에 추가한다. 관리자 화면의 수정값은 서버에서 우선 적용한다.
- API 검색은 별도 후속 단계. 식약처 영양성분 DB를 우선 후보로, USDA FoodData Central을 보조 후보로 둔다. 키는 서버 측에 보관하고 검색 결과는 기준량·제조사·출처를 확인받은 뒤 개인 기록에 저장한다.

### 운동·머신

- 빠른 검색 실패 시 `+ 신규 운동·머신 등록 요청`을 노출한다.
- `사진으로 요청`과 `직접 입력` 선택. 필수: 임시 이름 또는 제조사·모델 중 식별 가능한 정보. 선택: 타깃 부위, 헬스장, 사진, 메모.
- 제출 즉시 요청 ID와 `검토 대기` 상태를 표시한다. 관리자 요청함에서 중복 확인·자료 조사·승인/보류/반려 사유를 기록한다.
- 승인 시 공용 종목/머신 모델을 생성하고 필요하면 승인된 지점의 보유 머신으로 연결한다. 요청자의 기존 기록을 삭제하거나 덮어쓰지 않는다.
- 운동 강도는 머신 모델의 상수로 저장하지 않는다. 실제 세트 중량·횟수·선택적 RPE와 사용자의 이력으로 추정하고 `실제 근육 부하`로 단정하지 않는다.

## 보안·출시 순서

1. 현재 개인 계정만 허용하는 Firestore 규칙을 공용 읽기, 본인 요청 작성·조회, 관리자 승인·편집으로 분리한다. 관리자 여부는 화면 버튼이 아니라 서버 규칙에서 검증한다.
2. 사진은 Firebase Storage의 요청자·관리자 접근 규칙과 업로드 크기·형식 제한이 필요하다. 사진·헬스장 위치는 공개 승격 전 비공개로 둔다.
3. 먼저 로컬/테스트 환경에서 역할·공개 범위·과거 기록 보존을 검증한 뒤 배포한다. 운영 데이터 권한 변경은 별도 검토한다.
4. UI 간격·영양 D 색상·한글 검색 조합 오류·앞뒤 근육 미리보기는 독립 수정으로 먼저 처리한다.
