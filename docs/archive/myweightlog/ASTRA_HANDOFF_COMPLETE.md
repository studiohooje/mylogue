## 1. 대표님의 최종 제품 의도와 확정 결정

- **프로젝트 공식 이름:** `마웨로그`, 영문 `MyWeightLog`. 원래 대표님이 사용하던 [마웨그(MyWeightGraph)](https://woojehong.github.io/myweightgraph/)의 이름·색감·체중 그래프 경험을 계승한다. 초기에 이름 후보 10개를 요청했으나 이후 대표님이 `마웨로그/MyWeightLog`로 직접 확정했다. 다시 네이밍하지 않는다.
- **핵심 목적:** 체중·식단·운동을 매일 기록하는 습관을 만드는 1~2인용 앱. 본인 및 친구 한 명이 사용할 수 있지만 실제 계정·동기화는 아직 없다. 외부 공개나 수익화 목적은 없다고 밝혔다.
- **세 축:** (1) 몸/체성분: 체중·체지방률·골격근량 등의 날짜별 기록과 그래프, 마웨그 기능 일부 편입, InBody 결과지 사진의 수치화·추적. (2) 식단: 음식/끼니·총 kcal·탄수화물/단백질/지방 g와 열량 기준 비율, 목표·추세. (3) 운동: 번핏과 유사한 **기록 경험과 기능 범위**를 목표로 하는 종목/세트/루틴/분석/제안.
- **번핏 참고 범위:** 대표님은 번핏 **Pro** 기능까지 가능한 한 빠짐없이 조사하고, 같은 목적을 달성하는 자체 설계로 구현하라고 여러 번 명시했다. 픽셀 단위 UI, 번핏 에셋·GIF·코드·비공개 산식의 복사를 요구하는 최종 방향은 아니며, ‘자체설계로 해서 최대한 비슷하게 구현’으로 확정했다. 공개 자료만으로 모든 Pro 화면과 비공개 동작을 완전히 확인했다고 주장해서는 안 된다.
- **플랫폼:** Android에서 설치 가능한 APK와 iPhone에서 홈 화면에 추가해 앱처럼 쓸 수 있는 웹 앱/PWA의 투트랙. **APK는 iPhone에서 실행되지 않는다.** 웹 앱은 추후 GitHub Pages 게시 예정. 현재 게시하지 않았다. Android Studio Rabbit 2가 설치된 상태에서 개발했다.
- **데이터:** 우선 로컬에 저장하고 백업/복원; **최종적으로 서버 저장 및 기기간 동기화를 원함.** Firebase 등 백엔드 서비스는 나중에 대표님이 연결하기로 했으며 지금 계정·프로젝트·키·호스팅을 요구하지 않기로 했다.
- **AI:** 외부 AI API를 나중에 연결할 수 있도록 구조를 준비하되 현재 연결 여부는 나중에 결정. 별도 AI API 없이도 대표님이 이 채팅/Codex에 인바디 검사표를 주면 수치를 추출해 **마웨로그용 JSON 파일**을 만들고 앱에서 가져오고 싶어 한다. 나아가 Codex가 비서처럼 직접 입력하고 빌드·푸시·배포하는 자동화도 구상했으나, 앱을 만든 것만으로 채팅과 앱이 자동 연결되는 것은 아니다. 인증된 쓰기 API 또는 연결 도구, GitHub 권한, 배포 권한이 필요하다. 현재 직접 기록/푸시/배포는 구현하지 않았다.
- **워치:** 대표님은 Amazfit Bip Max로 추정되는 기기와 Zepp 앱, 친구는 Apple Watch 사용. 연동 가능성을 물었으나 **이번 범위에서는 워치 연동을 보류**하기로 확정했다. Zepp/Apple Health/Wear OS 실제 연동은 미검증이다.
- **작업 방식:** 기능을 잘게 모듈화. 중간에 멈추거나 사소한 확인을 요구하지 말고, 긴 시간이 걸려도 구현·러닝 테스트·검증·보고서를 한 번에 완료해 달라고 반복 요청했다. 대표님은 이번 로컬 개발 작업을 폭넓게 사전 승인했다. 다만 외부 공개·배포, 계정/자격증명 변경, 개인정보 외부 전송은 실제 단계에서 현재 지침과 승인 범위를 다시 확인해야 한다.

## 2. UI·브랜드 요구와 목업 결정

- 번핏 스크린샷의 **밀도 높은 운동 기록/결과 정보 구조**를 선호했다. 디자인까지 기계적으로 복제하지 않고 마웨그 계열의 자체 색과 브랜드로 구성한다.

- 서체 Pretendard, 감성 아이콘 Tossface 요청. **현재 CSS는 해당 폰트를 우선 지정하지만 폰트 파일/사용권 배포를 검증한 상태가 아니다.** 실제 로드 실패 시 시스템 대체 글꼴로 표시된다. 아이콘도 Tossface 파일 전체를 포함했다고 단정하면 안 된다.
- 최소 5가지 목업을 요구했고, 이는 한 디자인의 메뉴 5개가 아닌 **정보 구조/진입 방식 5가지 옵션**으로 만들었다. `mockups/index.html`에 `01 하루 대시보드(벤토+FAB)`, `02 기록 타임라인(칩)`, `03 빠른 입력(바텀 시트)`, `04 분석 캘린더`, `05 체성분 집중(인바디 확인)`이 있다. 대표님은 다 마음에 든다고 하면서 이를 바탕으로 실제 작동 프로토타입을 요청했다.
- 벤토 그리드, 바텀 시트, 칩, 토스트/스낵바, 스켈레톤, FAB 중 목적에 맞게 선택하라고 했다. 현재 앱은 요약 카드/바텀 시트/칩/토스트/FAB 등을 사용한다. 로딩 스켈레톤의 전 화면 완성 여부는 재검토해야 한다.
- 화면은 좁은 모바일 폭에서 숫자·단위와 한국어 줄바꿈이 무너지지 않아야 한다. 에뮬레이터에서 운동 입력 시트의 가로 넘침을 발견해 수정했다.

## 4. 요구의 시간순 변화 — 빠뜨리면 안 되는 대화 결정

1. 네이버 카페의 운동 결과 이미지가 보이는지 질문하고, 스크린샷으로 앱이 무엇인지 문의했다. 번핏 앱으로 논의가 이어졌다.
2. 번핏의 설립 시기·국내 개발 여부·유료 여부를 물었고, 자신이 만들고 싶었던 앱이 바로 이 경험이라고 설명했다. 이 역사/가격 정보는 이 개발 인수인계의 확정 기술 요구가 아니며 변동 가능하므로 필요한 경우 다시 공식 자료로 확인한다.
3. 처음에는 ‘번핏 기능 전부 파쿠리’라고 표현했으나, 개인·친구 1~2명용 비공개 비상업 앱임을 강조했다. 이후 **번핏 Pro 제공 기능을 철저히 파악하되 자체 설계로 최대한 비슷한 기능을 구현**하는 방향으로 확정했다.
4. 기존 마웨그와 비슷한 한·영 이름 후보 5개, 다시 10개와 이유를 요구했다. 이후 **마웨로그 / MyWeightLog**로 직접 확정해 폴더·프로젝트 이름도 지정했다.
5. 체중 기록/그래프, 식단 kcal·탄단지 g/%, 운동 기록, 인바디 사진 수치화·추적을 세 기둥으로 명시했다. 목적은 **기록하는 습관**이다.
6. 번핏의 기능을 큰 세 영역 아래 세부 동작까지 분해하고, 운동/식단을 **어떻게 입력하는지, 무엇을 추적하고 어떤 제안을 하는지** 문서화하라고 했다. 기존 마웨로그에 반영됨/가능하지만 미반영/반영 불가로 구분하라고 지시했다. 결과는 `FEATURE_INVENTORY.md`, `BURNFIT_PRO_GAP_ANALYSIS.md`에 있다. 후자는 **2026-10-31 초기 버전 상태표**로, 확장 뒤 상태가 아니다.
7. 목업 5종과 UI 패턴 선정, 위의 4색·Pretendard·Tossface 요구를 제시했다. 목업 전단계 파악 → 목업 → 실제 프로토타입 순으로 진행했다. 목업 5종은 옵션이며, 앱은 그중 한 화면을 무조건 고른 단일 시안이 아니라 유용한 구조를 결합했다.
8. Android를 사용하고, iPhone도 지원하길 원했다. APK 하나로 양쪽 OS를 지원할 수는 없으므로 Android APK + iPhone Safari 홈 화면 웹 앱/PWA로 확정했다. 웹은 추후 GitHub Pages, 서버는 추후 Firebase 등으로 연결하기로 했다.
9. 인바디 검사표를 Codex에 주고 마웨로그 업로드용 수치화 파일을 만들거나 Codex가 직접 입력해 주길 원했다. 현재 파일 가져오기 경로는 있으나 **Codex와 앱의 자동 연결·직접 쓰기·자동 배포는 없다.**
10. 장시간 자리를 비울 예정이라 추가 허락 없이 많은 구현·실행 테스트를 끝까지 진행하라고 여러 차례 재확인하고 최종 승인했다. Android Studio Rabbit 2 설치를 알렸다.

12. 외부 AI는 나중에 선택할 수 있도록 미리 연결 구조를 준비하고, 지금은 Codex 기반 파일 생성/가져오기를 활용하는 방안을 논의했다. 워치 가능성을 물었지만 **워치는 보류**했다.
13. 이번 최신 지시에서는 ‘가능한 모든 자체 설계 기능을 지금 한 번에 구현하고 누락하지 말라’고 재강조했다. 현재 구현된 범위와 미구현 범위를 정직하게 구분하는 것이 인수인계의 핵심이다.

## 7. 실제로 구현된 기능 — 반드시 ‘있음’과 ‘검증됨’을 구분

### 7.1 몸/인바디

- 날짜별 체중, 체지방률, 골격근량, 체지방량, BMI, 인바디 점수, 내장지방 레벨, 기초대사량 등 수동 입력과 기록 삭제.
- 체중·체지방률·골격근량의 30일/90일/전체 그래프와 날짜 비교. 마웨그의 다중 스킨 기능은 요구되지 않았다.
- 제공된 InBody 270 레이아웃의 사진을 기기 내 Tesseract OCR로 지정 영역 인식 → 수치 미리보기·수정 → 사용자 확정 저장. 제공 샘플의 주요 수치는 Node OCR로 검증했다. 전화번호 등 식별정보는 기록 필드로 가져오지 않는다.
- Codex가 작성한 `myweightlog.body` JSON 가져오기 경로.
- 진행 사진은 IndexedDB에 저장해 비교·개별 다운로드·삭제 가능. **사진은 일반 기록 JSON 백업에 들어가지 않는다.**

### 7.2 식단

- 날짜·끼니·음식명·메모, 1회 영양값(kcal/탄/단/지)과 섭취 수량·단위, 합계 미리보기, 저장·수정·삭제.
- 최근 입력한 음식·사용자 음식 프리셋 재사용. 검증된 외부 음식 영양 DB가 아니다. 보충제 기록 UI는 코드/기기에서 세부 흐름을 다시 확인할 것.
- 일일 총량, 탄단지 g와 열량 비율, 목표/잔량 성격의 표시, 7·30일 식단 추세, 주·월 사실 요약. 열량 비율은 탄수화물 4 kcal/g, 단백질 4 kcal/g, 지방 9 kcal/g 기준.
- Codex `myweightlog.meal` 버전 1 파일을 가져오면 검증 후 입력 화면에서 확인·수정해 저장. 자동 영양 추정은 아니다.

### 7.3 운동

- 직접 세션 기록: 날짜·제목·시간·메모/컨디션, 종목·부위, 중량·반복·세트 유형·RPE, 완료 체크, 세트 복사, 운동 세션 수정·삭제.
- 자체 운동 카탈로그 약 46종(코드에서 정확한 수량 재확인), native datalist 검색/선택, 종목별 지난 세트 참고, 과거 운동/루틴 재사용.
- 유산소 시간·거리, 슈퍼세트 그룹, 휴식 타이머. 타이머의 백그라운드/알림 신뢰성은 실기기 미검증.
- 사용자 루틴, 자체 입문 프로그램 3종, 자체 계산 규칙 기반 편집 가능한 세트 초안 6종, 바벨 원판 계산. **프로그램의 장기 주차별 진행·방대한 라이브러리는 별도 검토 필요.**
- 볼륨·세트·반복·추정 1RM/3대, 종목 추세, 부위별 볼륨, 주·월 사실 요약, 결과 PNG. ‘피로/회복’ 비슷한 기록 간격/RPE 지표는 실제 의학적 상태를 측정하지 않는다.
- Codex `myweightlog.workout` 버전 1 파일 검증·검토 후 저장.

### 7.4 공통

- 홈/캘린더/분석/설정, 바텀 시트 빠른 기록, 날짜별 기록, 로컬 저장 및 JSON 백업·복원.
- 웹은 정적 `app/dist/`로 빌드되며 GitHub Pages에 게시 가능한 구조. PWA manifest/service worker는 웹용. Android 네이티브 WebView에서는 이전 버전 캐시 문제 때문에 새 서비스 워커 등록을 중단했다.
- 외부 AI 연결용 `createAIAdapter(endpoint)`와 작업별 결과 검증은 존재하지만, 서버/키/모델 없이 **실제 AI 서비스를 제공하지 않는다.**

### 미검증·주의

- 실제 대표님 Android 휴대폰에서 최신 APK의 전체 입력·수정·삭제·파일 가져오기·백업/복원·카메라 OCR·사진 비교·타이머를 끝까지 검증하지 않았다.

- APK 구버전→신버전 업그레이드 때 WebView 서비스 워커가 오래된 UI를 보여주는 문제를 발견해 `MainActivity.java`에서 기존 서비스 워커와 `myweightlog-*` 캐시를 제거하도록 했다. **구버전의 실제 사용자 데이터가 있는 상태에서 업그레이드 후 보존을 검증하지 않았다.** `adb pm clear`는 에뮬레이터 테스트에만 썼으며 사용자 기기에 해서는 안 된다.
- 진행 사진은 IndexedDB에 있고 기록 JSON 백업 대상이 아니다. 기기 이전/복구 설계를 보강해야 한다.
- `npm audit --omit=dev`는 초기 보고 당시 0 취약점이었다. 현재 의존성 보안 상태는 시점에 따라 바뀌므로 재확인한다.
- 외부 웹 게시, Firebase/서버 연결, AI API, 워치 연동, 사용자 2명 간 동기화는 실시하지 않았다.

## 14. 최신 추가 지시 — 머신·근육 그림체, 선택형 입력, 피로 기반 제안

대표님은 경쟁 기능 표를 확인한 뒤 다음을 추가 요구했다. **Astra가 그대로 맡아 구현할 수 있게 파일에 반영하는 것**이 이번 채팅의 최종 작업이다. 자세한 화면·데이터·검증 명세는 [피트니스 플랫폼 조사·보완 제안의 W2a~W2c, §4~§5](FITNESS_PLATFORM_RESEARCH_2026-11-01.md)에 적었다. 아래 항목은 현재 앱의 구현 완료 목록이 아니다.

1. **머신 종류·제조사·모델:** 같은 운동 동작에도 여러 회사/모델 머신을 등록·선택할 수 있어야 한다. 제조사·모델명/번호, 헬스장·위치, 저항 형태, 사용자 사진을 선택적으로 저장한다. 모르는 머신도 기록을 막지 않는다. 머신별 기록과 동작 전체 기록을 구별해 본다.
2. **머신 사진 식별:** 사진을 찍거나 올려 제조사·모델 후보를 얻고 사용자가 맞는지 확인·수정한다. 불명확하면 ‘모름/직접 입력’을 제공한다. 현재 외부 AI/API나 충분한 머신 이미지 DB가 연결된 상태가 아니므로 **자동 인식 작동 완료라고 주장하면 안 된다.** 사진 속 다른 사람·시설 정보와 외부 전송 여부를 다뤄야 한다.
3. **kg/lb 모두 선택:** 운동 세트마다 원래 입력 숫자·단위를 저장하고 화면에서 kg/lb를 선택·전환한다. `1 lb = 0.45359237 kg` 기준으로 합계 계산을 일관되게 하되 반올림 왕복으로 원본값을 잃지 않는다. 머신의 레버비/저항 구조 차이 때문에 모델 간 표기 중량을 동일한 실부하로 취급하지 않는다.
4. **마웨로그 고유 그림체:** 자체 SVG/벡터 인체 전·후면과 머신 도감을 만든다. 프리웨이트/머신 운동 모두 주 타깃 근육을 **빨강**으로, 보조 타깃은 구분되는 패턴·명암으로 표시한다. 기존 검정·밝은 회색·두 보라는 브랜드 프레임으로 유지한다. 색만으로 의미를 전달하지 않고 근육 이름·접근성 라벨을 붙인다. 번핏/타사 그림의 포즈·윤곽·에셋을 트레이싱하지 않는다. 현재 그림 자산은 **아직 제작되지 않았다.**
5. **선택형 운동 입력:** 직접 타이핑이 중심인 현재 흐름을 `최근/즐겨찾기/루틴/몸 부위/장비` 선택→그림에서 근육/종목 선택→머신 모델 선택→전회 세트·루틴 목표를 편집 가능한 시작값으로 불러오기→중량 kg/lb·횟수·유형·RPE를 칩/스텝 버튼으로 선택→세트 완료·타이머 순서로 바꾼다. 텍스트 검색과 수동 수정은 남긴다. 중간 종료 시 임시 세션이 복구돼야 한다.
6. **다음 운동 제안에 피로와 상태 반영:** 완료 세트·중량·반복·RPE·주/보조 근육·지난 운동 날짜로 **부위별 운동 부하를 추정**할 수 있다. 여기에 사용자가 입력한 수면·에너지·근육통·통증/부상 우려·컨디션을 함께 사용해 추천 부위/종목/세트·중량 초안을 만든다. 근거·빠진 데이터·사용자 수정/건너뛰기를 표시한다. 기록 숫자만으로 실제 회복/건강을 확정할 수 없으므로 의학적 회복률처럼 표현하지 않는다. 통증/부상 우려에는 증량 추천을 내지 않는다. 외부 AI 없이 설명 가능한 규칙 기반 첫 버전은 구현 가능하다.
7. **우선순위 갱신:** 데이터 보존 P0 다음, 머신 수동 프로필·kg/lb·선택형 입력·근육/머신 그림체를 P1에 포함한다. 사진을 통한 모델 자동 식별은 데이터/API·정확도 검증이 필요한 P3 연결 기능으로 분리한다. 컨디션 입력과 설명 가능한 추정 부하·추천은 P2. 운동 자세 GIF·커뮤니티는 여전히 후순위다. 이 구분은 개발 의존성에 따른 제안이며 대표님의 요구를 삭제한 것이 아니다.

**Astra 검증 기준:** 실제 Android와 iPhone에서 머신 등록→사진 후보/수동 확정→kg/lb 혼합 세트→기록/재실행/백업/복원, 프리웨이트·머신의 빨간 근육 표시, 선택형 3세트 입력, 컨디션 좋은 날/나쁜 날/통증·기록 부족일 추천 분기를 테스트하고 결과를 문서화한다. 외부 AI를 연결하지 않았다면 사진 자동 식별은 미구현으로 보고해야 한다.
